## Additional Gaps Discovered

- An API process crash after creating an `UPLOADED` database row but before enqueue completion can strand the report because stale reconciliation currently scans only `QUEUED` and `PROCESSING` records. This is a Phase 3 candidate, not fixed in Phase 1.
- Upload and explicit retry publish or ensure a queue job before unconditionally writing `QUEUED`; a fast worker can write `PROCESSING` first and then have that state regressed to `QUEUED` by the API.
- AI extraction permits a null report date, but the verification input currently requires a date; the web form initializes only when a date exists. This is a Phase 3 regression case.
- Verification compares submitted measurement count and membership but does not require unique submitted IDs; duplicate IDs can defeat the intended exact-set check.
- Prescription exclusion is based on the client-selected stored document type. A prescription mislabeled as `REPORT` can enter report analysis; no independent semantic classifier or confirmation barrier exists.
- The coordinated document-deletion API exists, but the current web UI exposes no deletion control.
- A deterministic BullMQ job ID exists, but no distinct request-to-job correlation identifier is propagated.
- `documentVersion` is a concurrency/idempotency token currently defaulting to `1`; the repository does not implement user-visible document revision history or retain multiple extraction versions per document.
- A stale `PROCESSING` or `QUEUED` record with a live BullMQ job is intentionally left unchanged by reconciliation; this no-op outcome must remain explicit in lifecycle contracts.
- If a report-date tie straddles the 12-group boundary, the database query has no secondary ordering for deciding which tied groups enter the returned set.
- `GET /health` is static liveness only, while the root HTML currently says the backend is “ready”; dependency readiness is not implemented and the copy must not be treated as evidence.

## Phase 1 Validation Boundary

The corrected working SRS was checked against the files cited above, the current route and model inventories, the existing repair tracker, and the environment/privacy documents. No live service, hosted database, Supabase policy, patient workflow, or cross-device scenario was exercised as part of this specification-only phase. Those claims therefore remain implemented, blocked, future, or unverified according to their evidence.
